## 2. Deep Dive: Architectural Incompatibilities & Flawed Assumptions

### 2.1 [CRITICAL] The Needle Engine Dilemma: Invariant Violation, Dual Three.js Trees, and Commercial Licensing

#### Evidence & Audit Findings
1. **Direct Invariant Violation**:
   - [`AGENTS.md`](file:///home/sprime01/projects/gauntlet-game-studio/AGENTS.md) Section 5 and `REQ-RUNTIME-004` mandate:
     > *"The project runtime MUST resolve one authoritative Three.js dependency graph. Do not introduce hidden duplicate `three` installations."*
   - Live query of `@needle-tools/engine@6.0.0-alpha.3` from NPM registry reveals its exact `dependencies`:
     ```json
     {
       "three": "npm:@needle-tools/three@0.185.2-alpha.1",
       "three.quarks": "0.17.0",
       "three-mesh-bvh": "0.9.7",
       "@dimforge/rapier3d-compat": "0.19.3",
       "postprocessing": "6.39.0",
       "n8ao": "1.10.1"
     }
     ```
   - `@needle-tools/engine` **pins a proprietary fork of Three.js** (`@needle-tools/three`) in its direct `dependencies`. When installed via `pnpm`, this creates a shadowed, aliased `three` instance separate from the project's standard `three` (e.g. `three@0.186.0`).
   - Objects constructed by standard Three.js packages (`three-mesh-bvh`, `three.terrain.js`, `three.quarks`, or code generated by `img2threejs`) will fail `instanceof THREE.BufferGeometry` or `THREE.Object3D` checks when passed to Needle Engine, causing silent rendering dropouts and runtime crashes.
2. **Commercial Licensing Landmine**:
   - Gauntlet Game Studio is licensed under Apache-2.0 ([`LICENSE`](file:///home/sprime01/projects/gauntlet-game-studio/LICENSE)).
   - Needle Engine is a **proprietary commercial product**. The free Community license:
     - Enforces an un-removable **Needle branding watermark** rendered into the canvas.
     - **Strictly prohibits commercial use** (any revenue, client work, or commercial distribution requires paid monthly/annual Pro/Enterprise licenses).
   - Binding `REQ-BIND-001` to Needle Engine tethers an open studio to a proprietary runtime, injecting commercial restrictions and forced branding into every game generated by the studio.

#### Blast Radius
- Task `T04` (Redesign trigger specifically warned: *"If Needle requires a private Three.js fork/API surface that representative img2threejs/3dviz output cannot consume under one resolved runtime, stop before runtime implementation..."* — this condition is already met today).
- Task `T06` (Runtime integration) will immediately fail tooth check: *"Attempt to create runtime objects from a second Three.js package instance -> Expected: Compatibility guard/test fails."*

#### Actionable Recommendation
- **Decouple from Needle Engine as the default runtime**: Replace `@needle-tools/engine` with standard, community-standard Three.js + Vite + `@dimforge/rapier3d-compat` + Koota.
- Relegate Needle Engine to an optional, secondary export adapter (`adapter.needle`) for users who explicitly opt into Unity/Needle workflows and hold appropriate commercial licenses.

### 2.2 [HIGH] The Dual-Authority Paradox: Needle Engine vs. Koota ECS vs. Rapier

#### Evidence & Audit Findings
- The plan states in `T06` and `REQ-RUNTIME-001`:
  > *"Authoritative gameplay state MUST remain separate from Three.js/Needle scene objects, Rapier bodies, Recast navmesh objects, Blender objects, and other execution projections."*
- Needle Engine is fundamentally designed around Unity's component architecture:
  - Objects inherit from `Behaviour`.
  - Needle controls the frame loop (`awake()`, `start()`, `update()`).
  - Needle bundles its own internal Rapier physics world (`@dimforge/rapier3d-compat: 0.19.3`) and syncs rigidbodies to scene objects automatically during its update loop.
- Simultaneously, the plan mandates:
  - `Koota` is the authoritative game state ECS.
  - Rapier is the authoritative physics world for rovers, triggers, and obstacles.
- **The Paradox**:
  - If Needle ticks its internal Rapier world, Koota cannot control the physics stepping, collision dispatch, or rewind/scenario resets without fighting Needle's loop.
  - If Koota manages its own Rapier world, there are **two duplicate physics simulations running simultaneously**, causing severe performance penalties and desynchronization.
  - If Needle's component system and physics are disabled so Koota can run, Needle is reduced to a GLTF loader with a commercial watermark.

#### Actionable Recommendation
- Re-architect the runtime kernel around a pure, lightweight Three.js loop:
  `Koota (Authoritative State) -> Systems (Input, Rapier Physics, Recast Nav, Game Logic) -> Projection (Three.js Scene Graph + Audio + VFX)`.

## 3. Tooling & Ecosystem Realities: Library-by-Library Audit

An exhaustive audit of every library, package, and tool named in the plan was conducted against the npm registry, GitHub repositories, and runtime execution environments.

### 3.1 `three.terrain.js` (v3.1.1) vs. Rapier Heightfields
- **Library Reality**: `three.terrain.js` (authored by Isaac Sukin) generates `THREE.PlaneGeometry` meshes with vertex offsets using 2D canvas/simplex noise algorithms. It has no knowledge of modern physics engines.
- **The Gap**: Rapier3D's heightfield collider (`RAPIER.ColliderDesc.heightfield(nrows, ncols, heights, scale)`) requires:
  1. A 1D flat `Float32Array` of heights formatted in row-major or column-major grid order.
  2. Specific normalization of half-extents.
- `three.terrain.js` does NOT output this array directly; its geometry indices and vertex buffer format differ from Rapier's coordinate expectations.
- **Technical Debt**: Without an explicit heightfield serialization and transposition bridge in `packages/adapters/terrain`, Blackwater Relay's rover physics will either fall through the terrain or experience inverted collision normals.

### 3.2 `three.quarks` (v0.17.1) Version & Peer Dependency Clashes
- **Library Reality**: `three.quarks@0.17.1` declares `peerDependencies: { "three": ">=0.182.0" }`.
- **The Gap**: As observed in Section 2.1, `@needle-tools/engine` internally declares `"three.quarks": "0.17.0"`. If both Needle Engine and the studio's particle adapter instantiate `three.quarks`, particle systems will instantiate conflicting batch renderers, crashing the WebGL state.

### 3.3 `Tone.js` (v15.1.22) Autoplay Policies in Headless CI
- **Library Reality**: Modern browsers strictly enforce the Web Audio Autoplay Policy: `AudioContext` starts in a `suspended` state and can only be resumed via direct user gesture (`Tone.start()`).
- **The Gap**:
  - In headless Playwright runs (`pnpm --filter blackwater-relay test:e2e`), audio calls will remain suspended or throw exceptions unless Chromium is explicitly launched with `--autoplay-policy=no-user-gesture-required`.
  - In Node.js unit tests (`pnpm --filter blackwater-relay test:content`), `window.AudioContext` does not exist. Tests will crash on module import unless a Web Audio API mock (`standardized-audio-context-mock` or custom stub) is configured.

### 3.4 Asynchronous WebAssembly Initialization Hazards
- **Libraries Affected**: `@dimforge/rapier3d-compat@0.20.0` and `@recast-navigation/core@0.43.1` (`@recast-navigation/wasm`).
- **The Gap**:
  - Both libraries load WebAssembly asynchronously (`await RAPIER.init()`, `await init()`).
  - If Koota ECS worlds or entity spawners are initialized synchronously during page/test bootstrap, any instantiation of Rapier rigidbodies or Recast query filters will throw unhandled WASM memory access errors.
  - The plan lacks an explicit asynchronous lifecycle state for WASM subsystem readiness before scenario execution.

## 4. Upstream Agent Skills vs. Headless Gate Execution

### 4.1 The "Agent Skill" Execution Paradox in Automated Gates
- **Tasks Affected**: `T09` (`img2threejs`), `T10` (`3dviz-pro-max`), `T12` (`threejs-game-skills`).
- **Audit Findings**:
  - Upstream repositories `vendor/img2threejs`, `vendor/3dviz-pro-max`, and `vendor/threejs-game-skills` are **AI agent skill packages** (markdown instructions, prompts, and knowledge references intended for interactive agents like Claude Code or Codex).
  - Task `T09` defines the gate command:
    ```bash
    studio capability run asset.reconstruct.reference-image examples/blackwater-relay/.studio/requests/transceiver.yaml --json
    ```
  - **The Dilemma**:
    1. If `studio capability run` invokes a real LLM API to generate the procedural Three.js code from the reference image, it requires an external API key (Anthropic/OpenAI/Gemini), incurs financial costs, introduces 30–120s latency, and yields non-deterministic code outputs that break CI repeatability.
    2. If `studio capability run` does NOT invoke an LLM, it can only output a prompt handoff for an agent. In that case, `studio capability run` does not emit code, and the next gate command (`pnpm --filter blackwater-relay test:transceiver`) will immediately fail because no asset was created!
- **Resolution Needed**:
  The plan must clearly demarcate **Development Mode** (where the agent reads the skill and authors code) versus **CI/Conformance Mode** (where `studio capability run` replays a pre-generated, committed procedural asset fixture and verifies its metadata/integrity deterministically).

  - Mandating 20 distinct `pnpm` workspace packages from Day 1 introduces massive build tooling overhead: 20 `package.json` files, 20 `tsconfig.json` files, complex project references, circular dependency risks, and lengthy build times.
  - A pragmatic, leaner architecture would implement adapters as modules within `@studio/adapters` (or internal folders) until individual adapter reuse across multiple standalone repositories is genuinely required.
